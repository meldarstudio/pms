# Culqi checkout, verification, retries, and refunds

Documentation investigation dated 2026-10-27 for [Verify Culqi checkout, payment verification, retry, and refund contracts](https://github.com/meldarstudio/pms/issues/103), under [Wayfinder: online reservations and financial workflows](https://github.com/meldarstudio/pms/issues/109).

## Finding and verification limits

Cards and direct Yape have documented one-time token-to-charge integrations. Neither the ten-minute inventory deadline nor safe repeat charging after a lost response follows from that fact. Documentation does not establish a merchant idempotency key, a unique merchant-attempt lookup, authenticated webhook delivery, or a deadline for reconciliation. Yape refund eligibility remains unconfirmed. Cards have documented full and partial refunds, subject to operational and merchant constraints. These are documentation findings, not approval of launch methods. See the primary sources below.

No account login, API transaction, sandbox test, charge, refund, webhook delivery test, credential inspection, remote migration, secret change, or deployment occurred. Only public documentation and repository files were read. No application code changed. Unknowns below are prerequisites for later verification, not evidence that a capability is absent.

The [agreed baseline](https://github.com/meldarstudio/pms/issues/97) is Flexible at current rates with a first-night deposit, or Non-refundable at 10% off with full prepayment, and a ten-minute inventory and quote hold. Eligible refunds return the applicable deposit in full and the property absorbs processing costs. Pricing composition remains with [Decide rate-plan prices, discounts, and first-night deposits](https://github.com/meldarstudio/pms/issues/110).

## Checkout and payment methods

- [Custom Checkout](https://docs.culqi.com/es/documentacion/checkout/checkout-custom) captures card or phone details and returns a token for a backend charge. It exposes separate `tarjeta` and `yape` switches. Its `amount` and `currency: PEN` settings are required for Yape. The same page says omitting `order` displays only cards, yet associates `order` with PagoEfectivo, wallets and Cuotéalo. This is a documentation conflict, not proof that direct Yape requires a long-lived order. The older Custom URL linked from the API redirects here. Verify the current script with only card and direct Yape enabled before selecting it.
- [Token documentation](https://docs.culqi.com/es/documentacion/pagos-online/cargo-unico/tokens) gives both card and Yape tokens a five-minute lifetime and one use. A Yape token has an `ype_test_` or `ype_live_` ID even though the example calls its type `card`. Method provenance must use the actual integration and source identifier, not that type alone. A token is not evidence of payment.
- [Direct Yape documentation](https://docs.culqi.com/es/documentacion/pagos-online/cargo-unico/tokens-yape) requires a phone number and six-digit approval code. The code lasts at most two minutes. Direct Yape accepts PEN only, up to S/2,000. The token goes to the backend, which charges using the private key. These docs do not describe card-style 3DS for Yape. Do not impose or assume that flow without provider confirmation.
- The [official limits image](https://docs.culqi.com/images/pagos-online/limites-transaccion.png), linked by the [limits guide](https://docs.culqi.com/es/documentacion/pagos-online/limites-transaccion), lists Online card limits of S/6 to S/5,000, direct Yape up to S/2,000 with no numeric minimum, and different limits for PagoEfectivo wallets. Its card commission is 3.44% domestic or 3.99% foreign plus US$0.20 and IGV; direct Yape is 3.44% plus US$0.20 and IGV. These are published figures, not the merchant's contracted tariff. The API's generic bounds differ. Confirm actual limits for each method, including first-night deposits and discounted multi-night totals. A long stay may exceed Yape's ceiling. Splitting a payment is not an agreed workaround.

The PMS should calculate due-now in integer cents on the server and bind it to the held offer. Flexible requires one charge for the agreed deposit; Non-refundable requires one charge for the discounted full amount. These are applications of the baseline, not Culqi rate-plan products. Token and OTP expiry are separate from inventory expiry. Neither promises completion within ten minutes.

## Card 3DS and charge verification

[Culqi3DS overview](https://docs.culqi.com/es/documentacion/culqi-3ds/) calls integration mandatory and lets the fraud engine decide when authentication is needed. [The flow guide](https://docs.culqi.com/es/documentacion/culqi-3ds/flujo-con-3ds) says 201 means success and 200 requires 3DS. [The library guide](https://docs.culqi.com/es/documentacion/culqi-3ds/v1/uso-libreria) reverses those meanings. It instructs the merchant to repeat the charge with `authentication_3DS`, preserving the first `source_id` and device fingerprint. That documented continuation is distinct from retrying an unknown charge result. Do not implement success as any 2xx response or resolve the contradictory status table by guesswork.

[3DS configuration](https://docs.culqi.com/es/documentacion/culqi-3ds/v1/configuracion) uses the public key, charge amount, return URL and card email. It shows a message listener checking the current origin and receiving authentication parameters. A browser authentication callback is not payment verification. The backend still needs an authoritative successful charge. Its amount bounds also differ from the limits guide.

The [charge guide](https://docs.culqi.com/es/documentacion/pagos-online/cargo-unico/cargos) describes sending amount, currency, email and source token to create a charge. The [current official OpenAPI definition](https://apidocs.culqi.com/apiculqi.yaml), `POST /v2/charges`, accepts card or Yape sources and defaults `capture` to true. `GET /v2/charges/{id}` retrieves the charge using the private key. The charge schema includes ID, source, amount, currency, outcome, capture, refunds and metadata. It misspells the successful code as `succesfull_charge`; examples mix successful and declined fields, and the `paid` description incorrectly describes disputes. Establish actual payloads before fixing parser assumptions.

Design implication, pending the recovery decision: verify the server-created or server-retrieved charge against the expected merchant environment, held attempt, source, amount, PEN currency, successful outcome and capture state. Never let a browser supply a different amount or attach an arbitrary successful charge. Persist the charge ID and prevent reuse across reservations. A captured charge and a committed reservation are separate facts. Card authorization without capture is not received money. The API documents a four-day expiry for uncaptured card authorizations, which does not implement a ten-minute reservation hold.

## Notifications, duplicate delivery, and reconciliation

The [webhook guide](https://docs.culqi.com/es/documentacion/pagos-online/webhooks/) describes selecting event types and an endpoint in CulqiPanel. It does not specify a signature header, HMAC algorithm, shared-secret protocol, replay window, delivery ordering, retry schedule, acknowledgement timeout, retention period, or guaranteed delivery. Do not invent any of these or conclude that panel authentication cannot exist.

The [OpenAPI definition](https://apidocs.culqi.com/apiculqi.yaml), Webhooks and Events sections, lists `charge.creation.succeeded`, `charge.creation.failed`, `refund.creation.succeeded`, `refund.creation.failed`, and refund update events. It provides private-key `GET /v2/events/{id}` and paginated `GET /v2/events`. Notification `data` is a JSON string while retrieved event `data` is an object. Examples also vary event spelling. Verify actual payloads and normalize only observed/documented forms.

Recommended verification boundary: treat inbound notifications as untrusted prompts to fetch the event and affected charge or refund through the authenticated API. Match the fetched resource to a persisted attempt and expected money before applying a transition. Deduplicate durable event IDs and financial resource IDs, and re-read current state for stale/reordered events. Return acknowledgements only after durable receipt. Those are proposed PMS safeguards, not a documented Culqi delivery contract. Polling/reconciliation remains necessary if notifications never arrive. Bounds, staffing and guest messages remain human decisions.

## Lost charge responses and retries

The [OpenAPI definition](https://apidocs.culqi.com/apiculqi.yaml) has no idempotency parameter or header on charge/refund creation. Its `duplicated` flag only says the same information was charged before; it defines no comparison fields, deduplication window, retention, concurrency guarantee or safe retry procedure. A single-use token is not a documented exactly-once contract.

With a known charge ID, retrieve it. With no ID after a lost response, the API offers paginated charge listing filtered by time, amount, currency, email and other attributes, plus event listing and charge metadata. It documents neither `source_id` nor metadata nor a merchant-attempt key as a charge-list filter. Metadata can correlate returned candidates, but cannot guarantee timely visibility, uniqueness or completeness. Timestamp units differ between schemas and examples. Check pagination and time normalization in sandbox.

Proposed recovery requirements for [Decide inventory-hold, payment-recovery, and refund-escalation behavior](https://github.com/meldarstudio/pms/issues/113):

1. Persist an attempt and expected amount before sending the request. Include a non-secret attempt ID in charge metadata and retain the token/source ID as permitted by the verified integration. This supplies correlation, not provider uniqueness.
2. On timeout, disconnect or unparseable response, retain an unknown outcome. A missing local charge ID, expired token or absent webhook does not prove no charge occurred. Do not automatically obtain a fresh token and charge again.
3. Reconcile using charge/event listings and then retrieve candidates. Compare attempt metadata, source, money and environment. Multiple matches require investigation, not choosing the first. Zero matches do not establish failure without provider visibility guarantees.
4. Require merchant support or panel reconciliation when the API cannot identify the result. A later guest retry must follow the approved handling of the outstanding attempt, not bypass it.

Provider confirmation is required for any safe replay semantics, lookup guarantee, list consistency/retention bound and maximum unresolved interval. Existing D1 request receipts only deduplicate local commands; they cannot roll back or deduplicate Culqi effects.

## Refund eligibility, fees, and states

The [refund guide](https://docs.culqi.com/es/documentacion/pagos-online/operaciones/devoluciones/) advertises full/partial requests without a request fee. It describes same-day refunds as immediate with bank display lag, and later refunds as subtracting commission with a possible 15-to-30-day bank delay. That wording does not establish that the guest always receives the full requested principal.

The [OpenAPI definition](https://apidocs.culqi.com/apiculqi.yaml), `POST /v2/refunds`, requires `charge_id`, integer-cent `amount`, and a reason from `duplicado`, `fraudulento`, `solicitud_comprador`. It describes returning the amount and variable commission to the original credit/debit card, with partial refunds until the full charge has been returned. This is explicit card support. It does not explicitly establish full or partial refund support for direct Yape, destination, fees, or timing. Do not infer Yape refunds just because Yape uses the charges endpoint.

The refund object exposes `Completa`, `Pendiente`, `Rechazado`; list filters instead use `completado`, `pendiente`, `rechazado`. It includes refund ID, charge ID, amount and modification time. `GET /v2/refunds/{id}` and paginated refund listing support follow-up. Listing has no documented charge-ID filter; inspect returned objects. PATCH updates metadata, not a command to retry a rejected refund. Creation success or a creation event does not by itself establish final completion or the guest's bank credit.

The [published affiliation contract](https://www.culqi.com/static/files/terminos_y_condiciones_culqi_web.pdf), annex 5, section 3, PDF pages 33-34, adds material qualifications. It asks merchants to process refunds within 90 days and says later requests might not process. Refunds may require future settlements, reserves or prefunding. Requests may be rejected. Variable commission, and fixed commission for online products, are returned only before transfer to the merchant's bank account; afterward BCP is not obliged to return them. Its annulment cutoff is 16:00 on weekdays, not simply any time on the sale date. Confirm the merchant's applicable agreement and cutoff timezone. This is a published constraint, not legal advice or proof of this account's terms.

Consequences: do not promise fee-free economics, unlimited refund age, immediate bank credit or guaranteed acceptance. Reconcile the API's commission-return language with the guide and applicable merchant agreement. Preserve the agreed full eligible guest refund; do not silently deduct processing costs from the guest. If the provider cannot return the full required principal, a separately approved and evidenced fallback is needed. Future arrival dates can push cancellation beyond the provider's refund window even though a stay is limited to 60 nights.

For an ambiguous refund response, do not create another refund blindly. Retrieve/list refunds and the parent charge, compare returned amounts and outstanding obligations, and escalate when correlation is uncertain. Partial-refund support makes duplicate requests financially consequential. A pending or rejected refund is an obligation, not returned money. Unknown status strings also require reconciliation rather than automatic completion.

## Late success and failed-refund recovery

The provider documents no atomic reservation commit with D1, nor cancellation of an in-flight charge at the PMS hold deadline. A ten-minute hold is a PMS inventory rule. Closing Checkout or reaching ten minutes is not proof of payment failure. These are boundaries of the documented contract, not a selected lifecycle design.

The baseline requires recovery or refund when paid inventory cannot become a reservation. [Decide inventory-hold, payment-recovery, and refund-escalation behavior](https://github.com/meldarstudio/pms/issues/113) must choose whether/how to reacquire inventory after expiry, who handles late success, reconciliation bounds, retry permission and staff escalation. Do not confirm against inventory already sold to someone else. A Non-refundable rate does not justify keeping duplicate or unfulfillable payments. [Decide cancellation, no-show, and refund accounting](https://github.com/meldarstudio/pms/issues/111) owns the obligation/completed-refund accounting.

A rejected refund, insufficient funding, expired eligibility, or uncertain response needs a durable unresolved case, guest/staff communication and an accountable operator. The acceptable fallback method, approval, evidence and service deadline remain open human decisions. No automatic retry count or manual payout route is chosen here.

## Current code and payment provenance

[Payment storage](../../apps/backend/src/db/schema.ts) records method, optional reference, amount, payment date, notes and creation time. It has no Culqi charge ID, merchant environment, payment attempt or refund linkage. [Shared payment input](../../packages/shared/src/index.ts) treats reference as optional text. [Reservation save receipts](../reservations.md#concurrent-reservation-saves) protect local request replay. [The glossary](../../GLOSSARY.md#reservation-bill) defines recorded payments and credits, and current cancellation retains payments while zeroing the bill.

A staff-recorded `card` or `yape` payment is not established as a Culqi API charge. A free-text reference is not proof of provider origin. Refund routing must require verified provider provenance, or follow the separately agreed manual-payment process. Do not backfill provider IDs from method labels or silently reinterpret legacy credit as a completed refund.
